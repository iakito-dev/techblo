# ADR-0034: 記事カテゴリは職能軸の7種、保存済み要約から独立ステップで分類する

- **状態**: Accepted
- **決定日**: 2026-09-13
- **関連**: ADR-0010, ADR-0026, ADR-0027

## 背景

フィード画面を「新着 + カテゴリ別セクション(棚)」に作り変えるため、記事ごとに1つのカテゴリを持たせる必要が生じた。カテゴリ体系の検討は `design/category-taxonomy.md` にまとめられており、直近30日176件の手分類による実測検証を経ている。要点:

- 軸の候補として「技術レイヤー」「記事の目的・形式」「技術スタック」「職能領域(どのチームの仕事か)」を比較した。技術レイヤー単独では AI・セキュリティ・組織・イベントの記事(サンプルの約半分)が乗らず、記事の目的・形式は「解説」に6割以上が集中して棚として機能しない。
- 「職能領域」軸を採用した場合、最初に候補が2つ以上浮かんだ記事は 60.8%(旧7案)→ 43.2%、境界ルール(R1〜R8)適用後は 6.8% まで下がる。7カテゴリはいずれも 6〜20% の範囲に収まり、極端に薄い/厚い棚がない。
- 「イベント・コミュニティ」(協賛・登壇・参加/開催レポート)は量が16〜23%と大きいが、既存の技術軸カテゴリのどこにも収まらない(旧案では42件中37件が置き場に迷っていた)。

これを踏まえ、カテゴリ定義・保存方法・分類タイミング・レイヤー配置を決定する。

## 検討した選択肢

### 分類軸

#### A. 技術レイヤー(フロント/バックエンド/インフラ/データ)

- 直感的で定義が安定する
- AI・セキュリティ・組織・イベントの記事が乗らない(サンプルの約半分がはみ出す)

#### B. 記事の目的・形式(事例/解説/告知/組織論)

- 粒度は揃い、イベントも自然に吸収できる
- 「解説」に6割以上が集中し棚として機能しない

#### C. 技術スタック(AWS/Go/iOS 等)

- 既存のキュレーションタグ(`lib/tags/curated.ts`)と一致し親和性が高い
- 棚が細かすぎる(20超)。AWS棚に4割集中し、組織・AI活用の記事が乗らない

#### D. 職能領域(どのチームの仕事か)【採用】

- 技術・非技術・イベントが同じ抽象度(会社の中の役割)で並ぶ。記事の書き手は概ね1チームに属するため1記事1所属にしやすい
- 「AIでXをした」記事をXの職能側に置くための境界ルールが別途必要

### 分類タイミング・入力

#### E. 要約生成(本文取得+LLM)に相乗りさせる

- 呼び出し回数が増えない(1回のLLM呼び出しで要約+カテゴリを同時出力)
- 新着記事にしか適用できず、既存約2,400件のバックフィルには要約の再生成(本文の再取得)が必要になり、著作権配慮(ADR-0026)で避けたい全文再取得が発生する
- 要約プロンプトの複雑化(要約の品質とカテゴリ判定の責務が混在)

#### F. 保存済み要約(title + overview + tags)を入力に、独立ステップで分類する【採用】

- 新着とバックフィルが同じコード経路になる(本文取得を伴わない軽い入力なので全件再実行のコストが小さい)
- 要約生成とカテゴリ分類の責務・失敗が分離できる(要約が failed でもカテゴリ欄は無関係に保てる、の逆に要約が ready なら本文なしでも分類できる)
- 入力トークンが少なく安価(タイトル+概要1文+タグのみ)

### 配置

#### G. 新 feature `article-category` を新設する

- ai-summary と責務は分離されるが、実体は同じ `article_summaries` テーブルの1列で完結し、新 feature を割るほどの独立性がない

#### H. `features/ai-summary` の中に分類ステップを追加する【採用】

- 保存先(`article_summaries.category`)・入出力(要約)がすでに ai-summary の所有物であり、同一 feature に置く方が自然
- カテゴリの「定義」(表示名・並び順・棚か否か)は features 非依存にしたいため `shared/categories.ts` に切り出す(後述)

## 決定

**D(職能領域の7カテゴリ)+ F(保存済み要約からの独立分類ステップ)+ H(ai-summary 内に配置)** を採用する。

### カテゴリ定義

7キー: `ai`(AI・機械学習)/ `infra`(クラウド・インフラ)/ `devex`(開発生産性)/ `app`(アプリケーション開発)/ `security`(セキュリティ)/ `org`(プロダクト・組織・キャリア)/ `event`(イベント・コミュニティ)。

- 判断原則: 「この記事を読んだ人が持ち帰る知見は、どの職能領域(チーム)のものか」で決める。使っている技術・ツールではなく記事の主題(学びの中身)で決める。境界ルール(R1〜R8)は `design/category-taxonomy.md` §3・分類プロンプトは §6 に定義済みで、これをそのまま `LlmCategoryClassifier` のシステムプロンプトに用いる。
- 1記事は必ず1カテゴリにのみ所属する(複数選択・タグ的な多対多にはしない)。

### `event` を棚にしない理由

`event` は棚(フィード上の「見出し + 最新3本 + もっと見る」セクション)には表示せず、ページ下部のリストに置く。理由:

- イベント記事は量が16〜23%と大きいが、1本あたりの読む価値が他カテゴリより低く鮮度が命(参加/開催レポートは基本的に一度きりの話題性)。他の技術棚と同じ「3本カード」で並べると、新着に近い技術記事を押しのけてしまう
- `isShelf: false` という形でカテゴリ自体は分類対象に残し、表示ロジック側(feed/web、別担当)が棚一覧から除外するだけにする。分類とは独立して表示方針(3本カード/日付付き1行リスト/新着のみ表示等)を後から調整できる

### `shared/categories.ts` に置く理由(単一の真実の源)

カテゴリ定義(表示名・1行説明・棚の並び順・`isShelf`・Zod enum)は I/O を持たない純粋な定数モジュールであり、`features/ai-summary/domain`(分類結果の検証)と将来の `features/feed`(棚の描画)の両方から参照される横断的な設定でもある。

`lib/` は ADR-0010 の `domain-no-io` ルール(`bun run depcruise`)により `features/*/domain/` から import できない(`import type` も対象・`tsPreCompilationDeps: true`)ため、`lib/categories/` に置くと domain 層(`article-summary.ts` の `parseCategory` 等)がこの定義を参照できず、定義を domain 側にも複製する必要が生じてしまう。

一方 `shared/`(`shared/type-utils.ts`・`shared/result.ts` 等)は depcruise のどのルールからも禁止されておらず、`features/*/domain/` から import できる。カテゴリ定義はまさに `shared/` が想定する「feature 横断の純粋ロジック」そのものなので `shared/categories.ts` に置く。これにより:

- `features/ai-summary/domain/article-summary.ts` が `@/shared/categories` を直接 import し、`ArticleCategory` 型・`articleCategorySchema` を分類結果の検証にそのまま使える(独自定義・複製が不要)
- `features/ai-summary/infrastructure`・`db/schema/article-summaries.ts`・`trigger/`・`scripts/` など、他の参照元もすべて同じ `@/shared/categories` を見る
- 将来 `features/feed` が棚を描画する際も同じ定義(`CATEGORY_DEFINITIONS`, `SHELF_CATEGORIES`)を参照でき、カテゴリの追加・変更が1箇所で完結する(二重管理が発生しない)

### 分類は独立ステップにする理由

- 要約生成バッチ(`generate-article-summaries`, 10分毎)の後段に別 cron(`classify-article-categories`, 40分毎)として配置する。要約が `status='ready'`(overview/tags が確定)になった記事だけを分類対象にし、本文の再取得を伴わない
- 新着記事もバックフィル(既存約2,400件)も「未分類の ready 記事を取得して分類する」という同じ経路を通る。バックフィルは `AI_CATEGORY_BATCH_LIMIT` を一時的に引き上げて同じ cron を回すだけでよい
- 分類失敗(LLM 例外・enum 外出力)は `category=null` のまま `categorized_at` だけ更新して「試行済み」を記録する。`listUncategorizedArticleIds` は `categorized_at is null or categorized_at < now() - 1日` を再試行対象にすることで、同じ記事への無限リトライ・無限再課金を防ぐ

## 結果

- ✅ 新着・バックフィルが同一コードパスになり、実装・運用が単純になる
- ✅ 本文取得を伴わないため、要約生成に比べて分類バッチの入力コストが小さく、バックフィル(既存約2,400件)を一括で回しやすい(`AI_CATEGORY_BATCH_LIMIT` 最大200)
- ✅ カテゴリ定義(`shared/categories.ts`)が単一の真実の源になり、分類ロジック(`features/ai-summary/domain`)・DBスキーマ・将来の feed 側がすべて同じ定義を参照する(二重管理なし)
- ⚠️ 要約と分類が非同期に完了するため、新着記事は「要約は ready だがカテゴリは未分類」という中間状態がしばらく続く(最大で分類 cron の周期 + バッチ待ち程度)。表示側(feed、別担当)はカテゴリ null を「棚に出さない」扱いにする必要がある
- ❌ 既存約2,400件のバックフィルは本 ADR の実装範囲外(データ移行作業。マイグレーション適用後に運用でバッチ実行する)
