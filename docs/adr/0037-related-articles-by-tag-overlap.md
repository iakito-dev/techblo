# ADR-0037: 関連記事は AI要約タグの重なり + 同企業新着で選ぶ

- **状態**: Accepted
- **決定日**: 2026-10-05
- **関連**: ADR-0026, ADR-0027, ADR-0032, ADR-0034, ADR-0035, ADR-0036

## 背景

記事ページ `/a/[id]`(ADR-0036)は「元記事を開く」で終わる行き止まりで、読み終えた人の次の行き先が戻る導線しか無い。回遊(ページ/セッション)と内部リンク(SEO)を増やすため、ページ下部に関連記事を最大6件出したい。

既存資産として、AI要約が生成する表示タグ(`article_summaries.tags`、jsonb 文字列配列。ADR-0026/0027)と職能カテゴリ(ADR-0034)がある。一方で、埋め込みベクトルや記事間リレーションのテーブルは無い。DBスキーマ変更・マイグレーションは今回行わない。

## 検討した選択肢

### A. 埋め込みベクトルによる類似検索

- 内容: 要約から埋め込みを生成し pgvector で近傍検索する
- メリット: 表記ゆれに強く、意味的な近さを取れる
- デメリット: 新テーブル/列・拡張・埋め込み生成バッチ・バックフィルが必要。記事数に対して過剰で、運用コストと外部 API 依存が増える

### B. カテゴリ一致(職能軸7種)

- 内容: 同じ `article_summaries.category` の新着を出す
- メリット: 単純で索引も既にある
- デメリット: 粒度が粗く(7種)、ほぼ「同カテゴリの新着」になって関連性が感じられない

### C. 人気順(はてブ数・trend_score)

- 内容: 全体または同企業の人気記事を出す
- メリット: 実装が最小
- デメリット: 記事の内容と無関係になり、「関連」ではなく「おすすめ」になる

### D. AI要約タグの重なり数 + 同企業新着で補完【採用】

- 内容: 対象記事とタグを1つ以上共有する記事を「共有タグ数 降順 → publishedAt 降順 → id 降順」で取り、足りなければ同じ企業の新着で埋める
- メリット: 既存データだけで実装でき、スキーマ変更が不要。タグ数が多い記事ほど近いという直感に合う。補完があるのでタグ未生成・孤立した記事でも空にならない
- デメリット: タグの表記ゆれ(生成AI / LLM 等)は取りこぼす。意味的な近さは見ない

## 決定

D を採用する。選定は Repository の1クエリ(`listByTagOverlap`)で行い、補完は application 層(`listRelatedArticles`)が `list({ sort: 'latest', companyIds })` で行う。対象は `status='ready'` の要約を持つ記事だけで、自身と削除済みは除く。

`tags` に索引は足さない。GIN(jsonb)は `@>` のような包含検索向きで、「重なり数を数えて並べる」集計には効かないため、足しても全 ready 要約の走査は避けられない。代わりに `getRelatedArticles` を `'use cache'`(`cacheLife('days')`、`cacheTag(feed)`)にし、1記事あたりのスキャンを実質1回に留める。取込 cron の `revalidateTag(feed)` で新着は反映される。失敗時は記事ページを落とさず空配列を短命キャッシュ(`'minutes'`)で返す。

## 結果

- ✅ スキーマ変更・マイグレーション無しで、記事ページに回遊と内部リンクが増える
- ✅ 本文とは独立した Suspense でストリームするため、本文の表示を遅らせない
- ⚠️ キャッシュが効かない初回/無効化直後は全 ready 要約の走査になる。記事数が増えて遅くなったら下記の将来案へ
- ⚠️ タグの表記ゆれは取りこぼす(ADR-0032 の類義語グループ化は絞り込み側のみ。ここでは展開しない)
- ❌ 意味的な類似度は扱わない(受け入れたトレードオフ)

将来の余地: `tags` への GIN 索引、タグを正規化テーブル(`article_tags`)に切り出して結合+集計にする、類義語グループ(`lib/tags`)での正規化、規模が増えたらベクトル類似(A)への移行。
