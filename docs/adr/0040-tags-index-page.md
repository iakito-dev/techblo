# ADR-0040: タグ一覧ページ(/tags)を都度集計 + キャッシュで提供する

- **状態**: Accepted
- **決定日**: 2026-10-05
- **関連**: ADR-0027, ADR-0030, ADR-0032, ADR-0037

## 背景

カードや記事ページのタグは `/?tag=<タグ>` へのリンクになった(ADR-0027)が、「どんなタグがあるか」を見渡す入口が無い。企業ハブ `/companies`(ADR-0030)と同様に、タグのハブページを公開・SEO 対象として用意し、回遊と内部リンクを増やしたい。

タグは AI 要約(`article_summaries.tags`、jsonb 文字列配列)に入っており、タグマスタや正規化テーブルは無い。DBスキーマ変更・マイグレーションは行わない。

## 検討した選択肢

### A. 都度集計 + `'use cache'`

- `tags` を展開して group by し、`getPopularTags()` を `cacheLife('hours')` でキャッシュする
- メリット: スキーマ変更なし。ADR-0037(関連記事)と同じ方針で、鮮度は feed タグ失効に任せられる
- デメリット: キャッシュミス時は ready 要約の全件走査になる

### B. `tags` に GIN 索引 / タグ集計テーブルを追加

- メリット: 集計が速い
- デメリット: スキーマ・マイグレーション変更が必要。GIN は `@>` 向きで group by 集計には効かない。集計テーブルは取り込みバッチで更新する経路が増える

### C. 静的な固定タグ一覧(`lib/tags/curated.ts` のみ)

- メリット: 軽い
- デメリット: 実際に付いているタグ・件数を反映しない

## 決定

A を採用。`ArticleRepository.listPopularTags(limit, sinceDays?)` で集計し、`getPopularTags()` が直近90日(上位40)と全期間(上位120)の2系統を1キャッシュエントリで返す。ページは `/companies` と同じく `connection()` + Suspense で DB 非到達のビルドでも落ちない形にする。

- 索引を張らない理由: 走査はキャッシュミス時の時間単位1回で、記事数規模では許容できる。索引を足しても group by の全件展開は避けられず、書き込みコストだけ増える。
- 類義語展開はしない。表記ゆれは別タグとして並ぶが、遷移先の `?tag=` が `lib/tags/curated.ts` で展開するため絞り込みの取りこぼしは小さい。
- 件数は記事数(同一記事内の重複タグは1回)。空白タグは除外する。

## 結果

- ✅ スキーマ変更なしで公開ハブと内部リンクが増える
- ✅ 取得失敗でも空状態で返し、ページを落とさない
- ⚠️ 記事数が大きく増えたら、ミス時の走査コストを再評価する(件数上限は 200 に固定)
- ❌ 件数は集計時点のキャッシュで、最大1時間ほど古い場合がある
