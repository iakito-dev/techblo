# ADR-0029: 共有 OGP 画像は元画像があればホットリンク、無ければ自前生成

- **状態**: Accepted
- **決定日**: 2026-06-17
- **関連**: ADR-0004, ADR-0011

## 背景

記事プレビューページ(`/a/[id]`)の `og:image` / `twitter:image` は、これまで記事の OGP 画像有無に
かかわらず常に自前生成 API(`/api/og/[id]`)を経由していた。元画像がある場合は API 側で
1200x630 に cover 合成し、「共有時に必ず標準 OGP 比率になる」ことを担保する狙いだった。

しかしこの方式には次の難点があった。

- 元画像を cover 合成すると中央クロップで元の意図(図表・タイトル位置)が削れる
- 元画像があっても毎回 Satori で再描画するため生成コストが無駄
- 自前生成側のレイアウトが「元画像 cover」と「プレースホルダ」の二役を担い複雑

一方、フィードや記事詳細の画像表示は ADR-0004 のホットリンク方針(元画像をそのまま参照)を
採っており、共有 OGP だけ方針が異なっていた。

## 検討した選択肢

### A. 常に自前生成(従来)

- 共有時に必ず 1200x630 になる
- 元画像が任意比率でも見切れない…が、cover クロップで結局削れる
- 元画像ありでも毎回再描画するコスト

### B. 元画像があればホットリンク、無ければ自前生成

- 元画像はそのまま共有(作者の意図した構図を保てる、生成コスト 0)
- 任意比率の元画像は SNS 側でトリミングされ得る(多くは 1200x630 なので実害は小)
- 自前生成は「元画像が無い記事」専用になり、レイアウトを 1 つの目的に集約できる

## 決定

**B. 元画像があればホットリンク、無ければ自前生成** を採用。

`generateMetadata`(`app/a/[id]/page.tsx`)で `article.ogImage` の有無を分岐し、

- あり → 元画像 URL をそのまま `images` に指定(サイズは比率不明のため指定しない)
- なし → `/api/og/[id]` を 1200x630 で指定

`/api/og/[id]` は「元画像が無い記事」専用のプレースホルダ生成に役割を限定し、企業ファビコン +
企業名 + 日付のヘッダーに、タイトルを主役に大きく据えたカードを描く。元画像の cover 合成ロジックは
廃止した。

## 結果

- ✅ 元画像ありの記事は作者の意図した構図のまま共有され、生成コストもかからない
- ✅ 自前生成の役割が「タイトル主役のプレースホルダ」1 つに単純化した
- ✅ フィード・記事詳細(ADR-0004)と共有 OGP でホットリンク方針が揃った
- ⚠️ 任意比率の元画像は SNS 側でトリミングされ得る(標準比率でない元画像は将来 cover 検討の余地)
