# ADR-0046: ソフトウェアファクトリーの作業範囲を機能追加・UI/UX 改善に広げ、1 回の実行で複数 PR を出す

- **状態**: Accepted
- **決定日**: 2026-10-28
- **関連**: ADR-0045(このADRで範囲と本数を改める)

## 背景

ADR-0045 で始めたファクトリーは、1 回の実行で PR を最大 1 本、題材は不具合・テストの欠け・docs のずれなどの保守に限っていた。
運用 1 日目の 3 回はいずれも「テストの追加」で、自動マージまで問題なく通った。

オーナーからは、機能の追加と UI/UX の改善を進めてほしい、何を作るかの判断は任せる、1 日 1 本ではなくやれるところまで、という依頼があった。

UI を自律的に改善するには、変更後の画面を見て確かめる手段が要る。ところがクラウドのエージェント環境は、本番 DB にも RSS の取得先にも本番サイトにも届かない。

## 検討した選択肢

### 画面の確かめ方

- **A. Vercel の Preview デプロイを見る**: エージェント環境からは外部サイトに届かないことがあり、PR を出す前には確かめられない
- **B. 使い捨てのローカル環境を立てる(採用)**: 環境に入っている Postgres を `initdb` で起動し、マイグレーション・企業マスタ・デモ記事を入れて `next dev` を動かす(`scripts/sandbox.sh`)。Playwright で撮って見る

### 自動マージの扱い

- **C. 機能・UI の PR は一律で人のレビューにする**: 安全だが、小さな UI 改善まで人待ちになり、「やれるところまで」にならない
- **D. 既存の Factory guard(規模と保護領域)をそのまま使う(採用)**: DB・認証・依存・ADR を伴う機能は保護領域に触れるので自然に人のレビューへ回り、小さな UI 改善は自動マージできる。判定の仕組みは変えない

## 決定

**B と D** を採用し、`factory` スキルを次のように改める。

- 題材の優先順: `factory` ラベル Issue → 壊れているもの → UI/UX 改善 → 機能追加 → 保守(保守は 1 回 1 本まで)
- 1 回の実行で新しい PR は 5 本まで。open な人のレビュー待ち factory PR が 3 本を超えたら、自動マージできる作業だけを続ける
- UI を変えたら、サンドボックスで変更前後をモバイル / デスクトップ・ライト / ダークで撮って確かめる
- 好みが割れる見た目の変更は、規模が小さくても人のレビューに回す(エージェントの判断)
- 有料サービス・新しい外部 API キー・新しい環境変数が要るもの、既存機能の削除、デザインの全面刷新はやらない

## 結果

- ✅ 機能追加と UI/UX 改善がオーナーの起動なしに進む
- ✅ 自動マージの安全装置(Factory guard)は変えておらず、DB・認証・依存・ADR を伴う変更は必ず人が見る
- ✅ `scripts/sandbox.sh` は人の手元でも、本番データなしに画面を確かめる手段として使える
- ⚠️ 自動マージされた UI 変更は、人が見る前に本番(techblo.dev)へ出る。好みの割れる変更を人のレビューに回すかはエージェントの判断に依存する
- ⚠️ デモ記事は架空のデータで、企業アイコンなど外部に取りに行く画像は表示されない。本番に近い見え方の確認には Vercel の Preview が要る
- ❌ 1 回の実行が長くなり、使う計算資源が増える
